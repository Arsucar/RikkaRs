# Design: 全项目全流程全链路深度审查与优化

## 0. 目标架构

```
Phase A 审查（并行子代理）
  D1..D14 每域 1 个 general 子代理 → 输出结构化审计报告
Phase B 汇总定级（主代理）
  合并报告 → 按严重度分级 → 冲突/重复/回归去重 → 制定修复批次
Phase C 优化（并行实现子代理 + 主代理整合）
  Batch1 CRITICAL/HIGH → Batch2 MEDIUM → 每批聚焦测试
Phase D 验证（最后一个验证子代理跑 Gradle）
  编译 + 聚焦 JVM 单测 → 全量 JVM 单测 → 有设备 installDebug
Phase E 收尾
  review-report.md 归档 → spec 更新（可选）→ 用户确认 commit
```

## 1. 审查协议（每域子代理）

输入统一约定（写进每个子代理 prompt）：
- 工作目录固定；只读审查，**禁止任何编译/运行/写入**。
- 输出必须为 Markdown 结构化报告：`## 问题清单`（编号 F<域>-<n>、文件:行、严重度、描述、证据、建议修复）、`## 链路梳理`（该域主链路逐环节）、`## 亮点/可复用`、`## 遗漏与风险`。
- 严重度定义：
  - **CRITICAL**：崩溃/数据丢失/安全漏洞/API 契约破坏
  - **HIGH**：明确功能回归/竞态/资源泄漏/明显性能退化
  - **MEDIUM**：有复现路径的可控缺陷/低效
  - **LOW**：风格、死代码、可选抽象
- 禁止贴整文件；只贴关键代码片段（<30 行）。

## 3. 交叉验证点（主代理汇总时重点）

- D1↔D3：消息转换/截断/压缩双端一致性；#59 fork 压缩与上游阶梯是否共存。
- D1↔D9：会话持久化时序（branching、selectIndex 落库）。
- D4↔D5：工具执行与 workspace 安全边界。
- D3↔D12：API key 存储、provider 请求注入。
- D9↔D10：备份导出是否含全部 schema 字段、迁移链完整性。
- D11↔D1：流式 UI 更新与列表虚拟化。

## 4. 优化批次

- **Batch 1（CRITICAL/HIGH）**：编译错误、数据丢失、并发覆盖、安全问题、明确行为回归、验收契约冲突。
- **Batch 2（MEDIUM）**：有清晰复现路径且改动范围可控的缺陷；纯风格/命名/低收益清理不进入修复。
- **Batch 3（记录）**：LOW + 无直接证据的未来风险 → 写入 review-report 待办，不重启修复循环。

## 5. 验证策略

- 每批修复后只跑受影响模块聚焦 JVM 单测 + `:app:compileDebugKotlin`（仅最后一个验证子代理）。
- 全部修复完成后一次最终调用：资源处理 + Kotlin 编译 + 全量 JVM 单测 + AndroidTest 源码编译（如需）。
- 有设备 → `adb devices` → 无则 `adb connect 100.99.129.110:5555` → `installDebug`；失败重连固定端口重试一次，再失败如实报告。
- 不默认跑 `connectedDebugAndroidTest` / 全量 lint。

## 6. 风险与回滚

- 并行子代理并发写入同一文件 → 派发时每域分配不同文件子集；主代理最终整合 Edit。
- 编译大面积红 → 先回滚到 `10b33419`，分批提交修复。
- 修复被上游后续合并覆盖 → 在 review-report 标记并保持最小 diff。

## 7. 交付物

- `.trellis/tasks/<task>/review-report.md`：问题清单、已修复、已记录、验证证据、已知边界。
- 修复提交记录（按用户确认后 commit，不自动 push）。
